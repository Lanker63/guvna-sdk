# Epistemic Invariants

## Purpose

The Epistemic Invariants define the immutable laws governing the epistemic behavior of Guvna and Governed Repositories.

They establish the boundaries among:

- Repository Information;
- Evidence;
- Repository Knowledge;
- Repository Intelligence;
- Repository Wisdom;
- Repository Authority;
- Authority Decision;
- Acceptance;
- Repository Truth;
- Repository Understanding;
- Knowledge Manifestations;
- Realizations;
- Provenance;
- Uncertainty;
- and historical state.

All:

- Repository Intelligence models;
- Repository Understanding models;
- Repository Adoption processes;
- Semantic Contracts;
- Runtime implementations;
- SDK implementations;
- Host Implementations;
- repository governance;
- generated artifacts;
- projections;
- workflows;
- and other realizations

SHALL preserve these invariants.

These invariants are constitutional.

They are independent of:

- repository Domain;
- implementation technology;
- Runtime;
- SDK;
- Host;
- model provider;
- filesystem organization;
- transport;
- persistence;
- and deployment topology.

They define epistemic meaning.

They do not prescribe implementation.

---

# Foundational Epistemic Principle

Guvna SHALL preserve the distinction between:

```text
Repository Information
        │
        ▼
Reasoning
        │
        ├──────────────► Repository Intelligence
        │
        └──────────────► Repository Wisdom
                         │
                         ▼
                 Repository Authority
                         │
                         ▼
                    Authority Decision
                         │
                         ▼
                     Acceptance
                         │
                         ▼
              Accepted Repository Truth
                         │
                         ▼
                Repository Knowledge
                         │
                         ▼
             Repository Understanding
```

This is not a mandatory linear workflow.

It expresses the semantic relationship among the concepts.

In particular:

- Repository Information is available information.
- Evidence supports epistemic judgment.
- Repository Intelligence is derived reasoning.
- Repository Wisdom is informed judgment.
- Repository Authority is the authority capable of deciding repository-specific meaning.
- Authority Decision records that judgment.
- Acceptance is the constitutive transition that establishes accepted Repository Truth.
- Repository Knowledge is the durable epistemic memory of accepted Repository Truth.
- Repository Understanding is the contextual organization of accepted Repository Knowledge.

Repository Truth SHALL NOT be modeled as an inferential stage that automatically follows Intelligence or Wisdom.

---

# Invariant 1 — Repository Authority

Repository Authority is the authority capable of establishing Repository Truth for a Governed Repository within its applicable scope.

Repository Intelligence may inform Repository Authority.

Repository Wisdom may inform Repository Authority.

Evidence may support Repository Authority.

Models may assist Repository Authority.

Automation may facilitate Repository Authority.

None of these independently becomes Repository Authority merely by:

- reasoning;
- predicting;
- persisting;
- executing;
- or being trusted by the Host.

Repository Authority SHALL remain distinguishable from every mechanism that merely:

- observes;
- interprets;
- reasons;
- recommends;
- executes;
- persists;
- or projects.

---

# Invariant 2 — Authority Scope

Repository Authority SHALL be interpreted within its applicable scope.

Authority over one Governed Repository does not automatically establish authority over:

- Guvna constitutional doctrine;
- Guvna Semantic Contracts;
- unrelated repositories;
- unrelated Domains;
- Host Implementation;
- Runtime implementation;
- or SDK implementation.

Authority SHALL NOT be generalized beyond its accepted scope.

---

# Invariant 3 — Repository Information

Repository Information consists of information available to a repository that may contribute to repository understanding.

Repository Information MAY include:

- observations;
- declarations;
- records;
- artifacts;
- external references;
- historical information;
- execution results;
- measurements;
- conversations;
- or other information permitted by repository governance.

Repository Information MAY be:

- incomplete;
- conflicting;
- uncertain;
- transient;
- stale;
- historical;
- erroneous;
- or ambiguous.

Repository Information does not become Repository Knowledge merely because it exists.

---

# Invariant 4 — Evidence

Evidence is Repository Information that supports or informs an epistemic judgment.

Evidence MAY originate from:

- direct observation;
- repository artifacts;
- Runtime execution;
- external references;
- historical records;
- testing;
- measurement;
- authority interaction;
- model-assisted analysis;
- or other permitted sources.

Evidence SHALL remain distinguishable from:

- interpretation;
- Repository Intelligence;
- Repository Wisdom;
- Authority Decision;
- Acceptance;
- Repository Truth;
- and Repository Knowledge.

Evidence may support acceptance.

Evidence does not perform acceptance.

---

# Invariant 5 — Observation Is Not Interpretation

The observation of a condition SHALL remain distinguishable from an interpretation of that condition.

The distinction is:

```text
Observed Condition
        ≠
Interpretation
        ≠
Accepted Meaning
```

A repository artifact may demonstrate that something exists.

It does not necessarily establish:

- what it means;
- why it exists;
- whether it remains valid;
- or whether its interpretation has been accepted.

---

# Invariant 6 — Repository Knowledge

Repository Knowledge consists of durable knowledge representing Repository Truth accepted by Repository Authority.

Repository Knowledge is authoritative within its applicable repository and semantic scope.

Repository Knowledge SHALL preserve sufficient provenance to establish:

- what was accepted;
- under what authority;
- from what evidence or reasoning;
- under what semantic context;
- and when the acceptance occurred.

Repository Knowledge is intended to survive:

- implementation change;
- personnel change;
- technological change;
- repository reorganization;
- and the passage of time.

Repository Knowledge is not synonymous with any particular:

- file;
- database record;
- representation;
- Runtime state;
- or Knowledge Manifestation.

---

# Invariant 7 — Truth Is Authority-Established

Repository Truth is the authoritative status established by Repository Authority through Acceptance.

Repository Truth is not:

- an inference;
- a model prediction;
- a computational result;
- an implementation state;
- a filesystem state;
- a projection;
- a Runtime state;
- or a historical record merely because it exists.

The canonical relationship is:

```text
Repository Authority
        │
        ▼
Authority Decision
        │
        ▼
Acceptance
        │
        ▼
Repository Truth
```

---

# Invariant 8 — Truth Is Not a Processing Stage

Repository Truth SHALL NOT be treated as another processing state in a pipeline such as:

```text
Information
    ↓
Knowledge
    ↓
Intelligence
    ↓
Wisdom
    ↓
Truth
```

That formulation incorrectly implies that reasoning naturally produces Truth.

The constitutional relationship is:

```text
Information
    │
    ▼
Reasoning
    ├──────────────► Intelligence
    │                   │
    │                   ▼
    │                 Wisdom
    │                   │
    └───────────────────┘
                        │
                        ▼
                Repository Authority
                        │
                        ▼
                   Authority Decision
                        │
                        ▼
                    Acceptance
                        │
                        ▼
             Repository Truth
```

Intelligence and Wisdom may inform the authority process.

They do not produce Truth through progression alone.

---

# Invariant 9 — Authority Decision

Authority Decision is the authoritative judgment of Repository Authority regarding a proposition, Candidate Statement, or governed semantic subject.

An Authority Decision MAY:

- accept;
- reject;
- revise;
- defer;
- supersede;
- or otherwise resolve

a proposed meaning according to the applicable governance.

Authority Decision SHALL remain distinct from Acceptance.

The relationship is:

```text
Candidate Statement
        │
        ▼
Authority Decision
        │
        ├── reject
        ├── revise
        ├── defer
        │
        └── accept
                │
                ▼
            Acceptance
```

An `accept` decision authorizes the Acceptance transition.

It is not itself the resulting accepted knowledge.

---

# Invariant 10 — Acceptance

Acceptance is the constitutive epistemic transition through which Repository Authority establishes Repository Truth.

Acceptance SHALL be:

- explicit;
- attributable;
- scoped;
- provenance-preserving;
- and governed by the applicable Semantic Contract or repository authority mechanism.

Acceptance SHALL NOT be inferred from:

- model confidence;
- consensus;
- persistence;
- successful execution;
- UI completion;
- generated files;
- normalization;
- projection;
- or Runtime state.

The distinction SHALL remain:

```text
Authority Decision
        ≠
Acceptance
        ≠
Repository Knowledge
```

---

# Invariant 11 — Acceptance Produces Knowledge

Once Repository Authority performs the applicable Acceptance transition, the accepted meaning becomes Repository Truth and SHALL be preserved as Repository Knowledge.

The canonical relationship is:

```text
Authority Decision
        │
        ▼
Acceptance
        │
        ▼
Accepted Repository Truth
        │
        ▼
Repository Knowledge
```

Repository Knowledge is the durable epistemic memory of accepted Repository Truth.

---

# Invariant 12 — Repository Understanding

Repository Understanding represents the Governed Repository's current accepted understanding of itself.

Repository Understanding is derived from accepted Repository Knowledge.

Repository Understanding provides contextual structure through which Repository Intelligence can reason about the repository.

Repository Understanding SHALL NOT:

- replace Repository Knowledge;
- establish Repository Truth independently;
- or become a second authority source.

The relationship is:

```text
Repository Knowledge
        │
        ▼
Repository Understanding
        │
        ▼
Repository Intelligence
```

Repository Understanding evolves through accepted changes to Repository Knowledge.

---

# Invariant 13 — Repository Intelligence

Repository Intelligence is derived reasoning over available Repository Information and accepted Repository Knowledge.

Repository Intelligence MAY identify:

- relationships;
- implications;
- patterns;
- contradictions;
- dependencies;
- opportunities;
- risks;
- gaps;
- alternatives;
- hypotheses;
- and synthesized interpretations.

Repository Intelligence SHALL remain non-authoritative.

Repository Intelligence SHALL NOT independently establish:

- Repository Truth;
- Repository Knowledge;
- Repository Understanding;
- or Repository Authority.

---

# Invariant 14 — Intelligence Is Not Knowledge

Repository Intelligence SHALL remain distinguishable from accepted Repository Knowledge.

A result may be:

- useful;
- plausible;
- strongly evidenced;
- internally consistent;
- highly probable;
- or produced by a highly capable reasoning system.

None of those properties independently makes it accepted Repository Knowledge.

The distinction is:

```text
Repository Knowledge
        ≠
Repository Intelligence
```

---

# Invariant 15 — Repository Wisdom

Repository Wisdom represents informed judgment derived from Repository Intelligence and applicable Repository Knowledge.

Repository Wisdom MAY include:

- recommendations;
- preferred interpretations;
- strategic conclusions;
- prioritization;
- courses of action;
- risk judgments;
- and tradeoffs.

Repository Wisdom remains advisory.

Repository Wisdom SHALL NOT establish Repository Truth.

Repository Authority determines whether a recommendation or judgment becomes accepted repository meaning.

---

# Invariant 16 — Wisdom Is Not Authority

Repository Wisdom SHALL remain distinguishable from Repository Authority.

The distinction is:

```text
Repository Wisdom
        ≠
Repository Authority
```

Wisdom may inform a decision.

It does not become the authority merely because:

- it is persuasive;
- it is widely accepted;
- it comes from a trusted model;
- it has strong evidence;
- or it has repeatedly produced useful outcomes.

---

# Invariant 17 — Knowledge Manifestations

Repository Knowledge is communicated through Knowledge Manifestations.

Knowledge Manifestations are durable expressions of accepted Repository Knowledge.

Examples MAY include:

- constitutions;
- Repository Understanding;
- architectural descriptions;
- specifications;
- policies;
- legal doctrine;
- repository decisions;
- operational procedures;
- medical protocols;
- scientific methodologies;
- or other domain-specific knowledge artifacts.

The form of a Knowledge Manifestation is Domain-dependent.

A Knowledge Manifestation communicates accepted Repository Knowledge.

It does not establish Repository Truth merely by existing.

---

# Invariant 18 — Realizations

Realizations are operational or representational expressions of repository knowledge and understanding.

Examples include:

- implementations;
- source code;
- generated artifacts;
- workflows;
- diagrams;
- reports;
- Runtime behavior;
- visualizations;
- indexes;
- projections;
- caches;
- and filesystem structures.

Realizations MAY provide Evidence about the repository.

A realization SHALL NOT itself become epistemically authoritative merely because it exists, executes, persists, or is consumed.

The meaning represented by a realization MAY become accepted only through the applicable Repository Authority and Acceptance process.

The distinction is:

```text
Realization
    ≠
Accepted Meaning
```

and:

```text
Meaning Represented by Realization
        │
        ▼
Repository Authority
        │
        ▼
Acceptance
        │
        ▼
Accepted Repository Knowledge
```

This preserves the distinction between a representation and the accepted meaning represented by that representation.

---

# Invariant 19 — Provenance

Every governed epistemic transformation SHALL preserve provenance.

The provenance of:

- Repository Information;
- Evidence;
- Repository Knowledge;
- Repository Intelligence;
- Repository Wisdom;
- Authority Decisions;
- Acceptance;
- Repository Truth;
- Repository Understanding;
- Knowledge Manifestations;
- projections;
- and relevant realizations

SHALL remain observable to the degree required by the applicable Semantic Contract.

Provenance SHOULD identify, where applicable:

- source;
- authority context;
- transformation;
- semantic identity;
- semantic version;
- acceptance;
- and resulting manifestation.

Loss of required provenance is an epistemic integrity failure.

---

# Invariant 20 — Provenance Does Not Create Authority

Provenance explains where information came from and how it was transformed.

Provenance does not independently establish:

- Repository Truth;
- Repository Knowledge;
- Repository Authority;
- or Acceptance.

A perfectly traceable inference remains an inference until accepted.

A perfectly traceable observation remains an observation until its meaning is accepted where acceptance is required.

Therefore:

```text
Provenance
    ≠
Authority
```

---

# Invariant 21 — Uncertainty

Where evidence is insufficient, uncertainty SHALL be preserved.

Unknowns SHALL NOT be silently replaced by assumptions.

Incomplete understanding SHALL remain distinguishable from complete understanding.

Conflicting evidence SHALL remain distinguishable from resolved knowledge.

A model SHALL NOT convert uncertainty into certainty merely by producing a confident response.

---

# Invariant 22 — Multiple Interpretations

Where multiple interpretations remain supported by available information, those interpretations SHALL remain distinguishable until Repository Authority resolves them.

The system MAY:

- rank interpretations;
- identify confidence;
- recommend an interpretation;
- request clarification;
- or present alternatives.

It SHALL NOT silently collapse materially different interpretations into a single accepted meaning.

---

# Invariant 23 — Confidence Is Not Authority

Confidence, probability, statistical likelihood, model certainty, frequency, or repeated observation SHALL NOT be treated as equivalent to Repository Authority Acceptance.

The distinction is:

```text
Confidence
    ≠
Authority
```

A highly confident inference remains non-authoritative until accepted.

A low-confidence statement may nevertheless become authoritative if Repository Authority explicitly accepts it.

---

# Invariant 24 — Consensus Is Not Authority

Consensus among:

- models;
- agents;
- developers;
- tools;
- observations;
- executions;
- or automated systems

does not independently establish Repository Truth.

Consensus MAY inform Repository Authority.

Consensus does not replace Repository Authority.

---

# Invariant 25 — Automation Is Not Authority

Automation MAY:

- collect information;
- identify evidence;
- perform analysis;
- generate Candidate Statements;
- identify contradictions;
- normalize accepted knowledge;
- produce projections;
- or execute accepted directives.

Automation SHALL NOT independently establish Repository Truth.

Where automation performs an acceptance operation under an explicit authority mechanism, the authority remains attributable to Repository Authority.

---

# Invariant 26 — Artificial Intelligence Is Not Authority

Artificial intelligence, machine learning, language models, agents, classifiers, and other computational intelligence MAY assist with:

- observation;
- interpretation;
- synthesis;
- reasoning;
- recommendation;
- normalization;
- and interaction.

Artificial intelligence SHALL remain non-authoritative unless explicitly incorporated into an accepted authority mechanism.

Model output alone does not establish:

- Repository Truth;
- Repository Knowledge;
- Repository Understanding;
- Repository Governance;
- or Repository Authority.

Model confidence does not establish authority.

Model consensus does not establish authority.

---

# Invariant 27 — Runtime Is Not Epistemic Authority

Runtime MAY:

- evaluate governance;
- validate contracts;
- enforce invariants;
- evaluate authority state;
- produce Runtime Directives;
- execute accepted operations;
- and record Evidence.

Runtime SHALL NOT independently establish repository-specific Repository Truth.

Runtime MAY identify:

- contradiction;
- stale knowledge;
- semantic incompatibility;
- insufficient evidence;
- or changed conditions.

Such findings SHALL enter the applicable Repository Intelligence and authority process where repository meaning must change.

---

# Invariant 28 — SDK Is Not Epistemic Authority

SDKs MAY expose:

- Repository Information;
- Candidate Statements;
- Authority Decisions;
- Acceptance operations;
- Repository Knowledge;
- Repository Understanding;
- diagnostics;
- projections;
- and Runtime state.

An SDK does not become epistemic authority merely because it transports or exposes an acceptance operation.

The authority remains attributable to Repository Authority.

---

# Invariant 29 — Host Is Not Epistemic Authority

Host Implementations MAY:

- collect information;
- facilitate authority interaction;
- display Candidate Statements;
- present evidence;
- bind Conversational Inference Models;
- render projections;
- and present acceptance results.

Host Implementations SHALL NOT independently establish:

- Repository Truth;
- Repository Knowledge;
- Repository Understanding;
- Repository Governance;
- or Repository Authority.

Host presentation state SHALL NOT be treated as epistemic state merely because the Host displays it.

---

# Invariant 30 — Model-Assisted Interpretation Is Not Acceptance

A Conversational Inference Model MAY produce:

- interpretations;
- classifications;
- summaries;
- Candidate Statements;
- recommendations;
- or structured responses.

Those outputs remain non-authoritative until the applicable authority mechanism accepts them.

The canonical relationship is:

```text
Authority Interaction
        │
        ▼
Conversational Model
        │
        ▼
Structured Interpretation
        │
        ▼
Core Validation / Reduction
        │
        ▼
Candidate Meaning
        │
        ▼
Repository Authority
        │
        ▼
Acceptance
```

Model output SHALL NOT directly establish accepted Repository Knowledge.

---

# Invariant 31 — Normalization Does Not Establish Truth

Normalization MAY:

- canonicalize representation;
- establish semantic identity;
- normalize relationships;
- validate structure;
- or prepare accepted knowledge for downstream consumption.

Normalization SHALL NOT independently establish Repository Truth.

Where normalization changes semantic meaning rather than representation, the applicable authority mechanism SHALL be invoked.

---

# Invariant 32 — Projection Does Not Establish Truth

A Projection is a derived representation of accepted meaning.

Projection MAY produce:

- Governance Projections;
- Knowledge indexes;
- summaries;
- diagrams;
- guidance;
- Runtime-consumable representations;
- workspace views;
- or other derived artifacts.

Projection SHALL NOT establish Repository Truth.

A projection remains derivative of its accepted source.

---

# Invariant 33 — Persistence Does Not Establish Truth

Persistence does not establish epistemic authority.

The following SHALL NOT become authoritative merely because they are stored:

- files;
- database records;
- caches;
- indexes;
- logs;
- generated artifacts;
- Runtime state;
- SDK state;
- Host state;
- or model outputs.

Persistence preserves information.

Acceptance establishes repository-specific truth where acceptance is required.

---

# Invariant 34 — Execution Does Not Establish Truth

Execution produces evidence about what occurred.

Execution SHALL NOT independently establish:

- Repository Truth;
- Repository Knowledge;
- Repository Understanding;
- or Repository Governance.

The fact that an operation succeeded does not establish that the operation was semantically correct.

The fact that an operation repeatedly succeeds does not establish authority.

Execution Evidence MAY inform Repository Intelligence and Repository Authority.

---

# Invariant 35 — History Does Not Establish Current Truth

Historical acceptance remains evidence of what was accepted at a particular point in governed repository evolution.

Historical state SHALL remain distinguishable from current accepted state.

History does not automatically establish that a previously accepted statement remains current.

Changes to Repository Truth require the applicable authority and acceptance mechanism.

---

# Invariant 36 — Epistemic State Is Not Filesystem State

Filesystem organization SHALL NOT determine epistemic state.

A file does not become:

- Knowledge;
- Truth;
- Authority;
- or accepted understanding

merely because it exists at a particular path.

Filesystem identity and epistemic identity SHALL remain distinct.

---

# Invariant 37 — Semantic Identity Is Not Epistemic Authority

Semantic Identity establishes what an artifact represents.

It does not independently establish whether its represented meaning has been accepted.

The distinction is:

```text
Semantic Identity
        ≠
Authority
```

An artifact may have a stable identity while remaining:

- provisional;
- rejected;
- superseded;
- historical;
- or otherwise non-current.

---

# Invariant 38 — Supersession Preserves Epistemic History

When accepted Repository Knowledge is superseded:

- prior knowledge SHALL remain historically identifiable;
- the successor SHALL preserve its own acceptance provenance;
- the relationship between prior and successor SHALL remain explicit;
- and current state SHALL remain distinguishable from historical state.

Supersession does not erase epistemic history.

---

# Invariant 39 — Repository Understanding Is Mutable Through Acceptance

Repository Understanding may evolve.

Its evolution SHALL remain attributable to changes in accepted Repository Knowledge.

The conceptual transition is:

```text
Existing Repository Knowledge
        │
        ▼
New Evidence / Intelligence / Wisdom
        │
        ▼
Candidate Change
        │
        ▼
Repository Authority
        │
        ▼
Authority Decision
        │
        ▼
Acceptance
        │
        ▼
Updated Repository Knowledge
        │
        ▼
Updated Repository Understanding
```

A Runtime, Host, SDK, or model SHALL NOT silently mutate Repository Understanding outside this governed transition.

---

# Invariant 40 — Repository Understanding Is Contextual, Not Authoritative

Repository Understanding organizes accepted Repository Knowledge into a coherent contextual model.

It MAY provide:

- structure;
- relationships;
- classification;
- context;
- and semantic organization.

Repository Understanding does not replace the underlying accepted Repository Knowledge.

It does not acquire authority merely because it is the principal model consumed by Runtime.

---

# Invariant 41 — Domain Independence

These invariants apply independently of repository Domain.

They SHALL apply whether a Governed Repository concerns:

- software engineering;
- law;
- medicine;
- science;
- manufacturing;
- education;
- finance;
- infrastructure;
- research;
- or another Domain.

Domain-specific epistemic concepts MAY extend the model.

They SHALL NOT contradict these invariants.

---

# Invariant 42 — Domain Semantics Do Not Alter Epistemic Authority

A Domain may define its own concepts for:

- evidence;
- proof;
- precedent;
- observation;
- validation;
- judgment;
- or acceptance.

Those Domain concepts MAY specialize epistemic realization.

They SHALL NOT silently change the constitutional authority boundary.

Repository Authority remains the authority mechanism defined by the applicable repository governance.

---

# Invariant 43 — Guvna Authority and Repository Authority Are Distinct

Guvna Core owns Guvna semantics.

Governed Repositories own repository-specific truth.

These authorities SHALL remain distinct.

Guvna Core may establish:

- constitutional doctrine;
- Semantic Contracts;
- Projection Contracts;
- Runtime semantics;
- SDK semantics;
- Host obligations;
- and other Guvna-owned meaning.

Repository Authority establishes:

- repository-specific truth;
- accepted Repository Knowledge;
- Repository Understanding;
- Repository Governance;
- and repository-specific semantic decisions.

Neither authority silently replaces the other.

---

# Invariant 44 — Semantic Contracts Preserve Epistemic Boundaries

Semantic Contracts SHALL preserve the distinctions among:

- Information;
- Evidence;
- Knowledge;
- Intelligence;
- Wisdom;
- Authority;
- Authority Decision;
- Acceptance;
- Truth;
- Understanding;
- and Realization.

A valid schema or contract representation SHALL NOT cause a derivative realization to appear authoritative merely because it satisfies structural requirements.

Structural validity is not epistemic acceptance.

---

# Invariant 45 — Projection Contracts Preserve Epistemic Boundaries

A Projection Contract SHALL preserve the distinction among:

- source Repository Knowledge;
- Repository Understanding;
- Repository Governance;
- projected representation;
- provenance;
- projection validity;
- and accepted meaning.

Conformance to a Projection Contract establishes structural and semantic contract validity.

It does not establish Repository Truth.

A valid Governance Projection remains a derived representation of accepted repository meaning.

---

# Invariant 46 — Epistemic Evolution Is Governed

Changes to accepted Repository Knowledge SHALL occur through governed epistemic evolution.

The general pattern is:

```text
Current Accepted Knowledge
        │
        ▼
New Information / Evidence
        │
        ▼
Repository Intelligence
        │
        ▼
Repository Wisdom / Candidate Meaning
        │
        ▼
Repository Authority
        │
        ▼
Authority Decision
        │
        ▼
Acceptance
        │
        ▼
New Accepted Knowledge
```

The precise workflow MAY vary by Domain.

The authority boundary SHALL NOT vary without explicit governing doctrine.

---

# Invariant 47 — Semantic Evolution Does Not Automatically Change Repository Truth

Changes to Guvna Semantic Contracts SHALL NOT automatically alter repository-specific Repository Truth.

If a Guvna semantic evolution affects:

- Repository Understanding;
- Repository Governance;
- repository-specific constraints;
- or repository-specific Knowledge Manifestations

the affected repository SHALL undergo the applicable alignment process.

Repository-specific change remains subject to Repository Authority.

---

# Invariant 48 — Repository Alignment Preserves Epistemic Ownership

Repository alignment may identify:

- affected knowledge;
- affected understanding;
- affected governance;
- affected projections;
- or required repository-specific changes.

The alignment process SHALL NOT independently establish those changes as Repository Truth.

The canonical relationship is:

```text
Guvna Semantic Delta
        │
        ▼
Repository Impact Analysis
        │
        ▼
Candidate Repository Change
        │
        ▼
Repository Authority
        │
        ▼
Authority Decision
        │
        ▼
Acceptance
        │
        ▼
Updated Repository Knowledge
```

---

# Invariant 49 — Epistemic History Is Preserved

When epistemic state changes, the system SHALL preserve sufficient history to distinguish:

- prior Knowledge;
- current Knowledge;
- prior Understanding;
- current Understanding;
- prior Authority Decision;
- current Authority Decision;
- supersession;
- revision;
- rejection;
- and provenance.

Historical state SHALL NOT be silently rewritten to appear as though it were always current.

---

# Invariant 50 — No Realization Becomes the Source of Meaning Merely by Existing

No:

- file;
- directory;
- source code artifact;
- generated artifact;
- Runtime;
- SDK;
- Host;
- model;
- cache;
- index;
- workflow;
- projection;
- execution;
- or historical record

becomes the source of repository meaning merely because it exists, executes, persists, or is widely used.

Meaning remains attributable to:

- governing doctrine for Guvna-owned semantics; or
- Repository Authority and accepted Repository Knowledge for repository-specific semantics.

---

# Invariant 51 — Constitutional Supremacy

These Epistemic Invariants govern every Guvna epistemic activity.

Repository Intelligence Models, Repository Understanding Models, Repository Adoption, Semantic Contracts, Projection Contracts, Workspace agents, architectural decisions, Runtime implementations, SDKs, Hosts, Knowledge Manifestations, projections, and generated artifacts SHALL remain consistent with these invariants.

Where a lower-order realization conflicts with these invariants, these invariants prevail.

A realization SHALL NOT reinterpret a constitutional invariant merely to simplify implementation.

             └────────────┬────────────┘
                          ▼
                 REPOSITORY WISDOM
                          │
                          ▼
                 REPOSITORY AUTHORITY
                          │
                          ▼
                AUTHORITY DECISION
                          │
                          ▼
                     ACCEPTANCE
                          │
                          ▼
              ACCEPTED REPOSITORY TRUTH
                          │
                          ▼

                          │

                          │

It expresses the constitutional relationship among epistemic concepts.

> **Wisdom does not establish Truth.**

> **Authority establishes Truth through Acceptance.**

> **Knowledge preserves accepted Truth.**

> **Understanding organizes accepted Knowledge.**

> **Manifestations communicate Knowledge.**

> **Realizations provide operational expression and Evidence.**

The Repository Intelligence Model realizes these invariants through canonical concepts and transformations.

- the distinction between Knowledge and Intelligence;
- the distinction between Intelligence and Wisdom;
- the distinction between Wisdom and Authority;

- and the distinction between accepted Truth and its manifestations.

Repository Intelligence MAY challenge, extend, or recommend changes to Repository Understanding.

The Repository Understanding Model defines the canonical structure of current accepted Repository Understanding.

The Epistemic Invariants govern how that knowledge may be established and changed.

```text
Repository Authority
        │
        ▼
Acceptance
        │
        ▼
Repository Knowledge
        │
        ▼
Repository Understanding
```

The Repository Understanding Model SHALL NOT redefine:

- Repository Authority;
- Acceptance;
- Repository Truth;
- or epistemic provenance.

>
> **Evidence may support judgment.**
>
> **Intelligence may reason.**
>
> **Wisdom may recommend.**
>
> **Authority may decide.**
>
> **Authority Decision records that judgment.**
>
> **Acceptance establishes Repository Truth.**
>
> **Knowledge preserves accepted Truth.**
>
> **Understanding organizes accepted Knowledge.**
>
> **Knowledge Manifestations communicate accepted Knowledge.**
>
> **Realizations provide operational expression and Evidence.**
>
> **Provenance preserves lineage.**
