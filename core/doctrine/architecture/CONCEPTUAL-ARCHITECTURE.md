# Conceptual Architecture

## Purpose

This document is Architectural Doctrine.

It describes the enduring conceptual architecture through which Guvna Core realizes the accepted constitutional doctrine and canonical models.

It is a Knowledge Manifestation of accepted Repository Knowledge.

It does not establish Repository Truth.

It does not redefine constitutional doctrine or canonical models.

It does not prescribe implementation details, runtime behavior, or operational guidance.

This document is independent of programming language, implementation, repository organization, deployment topology, runtime technology, and host environment.

## Architectural Status

Architectural doctrine is subordinate to accepted constitutional doctrine and canonical models.

Architectural concepts are first-class concepts within this document.

Architectural concepts derive from accepted constitutional doctrine and canonical models but are not themselves constitutional or canonical unless the governing doctrine explicitly says so.

Architectural concepts shall be explicitly defined within this document.

Architectural concepts shall remain constitutionally and canonically traceable.

Architectural boundaries shall keep constitutional doctrine, canonical models, architectural doctrine, realization, and operational guidance distinct.

## Architectural Structure

The architecture is organized into four stable layers.

| Layer | Role | Representative concepts |
|------|------|-------------------------|
| Canonical Understanding Layer | Accepted repository understanding that grounds the architecture | Repository Understanding, Repository Identity, Domain, Mission, Vision, Operating Model, Authority Model, Governance Model, Knowledge System, Work System, Success Model, Provenance |
| Architectural Doctrine Layer | First-class architectural concepts and responsibilities | Architectural Doctrine, Architectural Concept, Constitutional Realization, Canonical Realization, Architectural Boundary, Architectural Ownership, Architectural Traceability, Architectural Separation, Architectural Invariant |
| Realization Layer | Downstream realization of architectural doctrine | Workflow Definition, Workflow Instance, Runtime, Dispatcher |
| Evidence and History Layer | Immutable trace of realization and architectural evolution | Execution Record, Evidence, Architectural History |

The canonical understanding layer precedes architectural doctrine.

Architectural doctrine organizes realization.

Realization produces evidence.

Evidence preserves provenance.

History preserves accepted architectural evolution.

## Realization Concepts

### Workflow Definition

A Workflow Definition is an immutable realization of an accepted operational pattern.

It organizes current work without redefining the canonical model it realizes.

Traceability: Work System, Governance Model, Knowledge System, Architectural Doctrine.

### Workflow Instance

A Workflow Instance is a mutable occurrence of a Workflow Definition that carries current state, progression, and evidence references.

Traceability: Work System, provenance, and accepted architectural realization.

### Runtime

Runtime is the realization boundary that executes the operations required by Workflow Instances.

Traceability: realization, execution, and accepted architectural boundaries.

### Dispatcher

Dispatcher is the mechanical executor used by Runtime to invoke authorized operations.

Traceability: realization only; it does not own governance or authority.

### Execution Record

An Execution Record is an immutable runtime artifact that captures what occurred.

Traceability: Realizations, provenance, and evidence.

### Evidence

Evidence is a durable record that communicates realization and preserves provenance.

Accepted understanding is represented by the accepted canonical and architectural artifacts that the evidence records, not by the evidence record itself.

Traceability: Repository Knowledge, Realizations, and accepted understanding.

### Architectural History

Architectural History is an immutable sequence of accepted architectural changes, evidence, and provenance links.

Traceability: Provenance, accepted Repository Knowledge, and Repository Understanding.

Architectural History preserves the fact and provenance of accepted change; it remains derivative of accepted understanding rather than a replacement for it.
